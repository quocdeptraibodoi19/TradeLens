# TradeLens Learning Log

- 2026-08-28 — Analytics-engineering flow (EL → dbt T → serve) — learned: dbt never ingests, only transforms what's already landed; alembic owns landing_zone DDL, dbt owns derived layers (source boundary = alembic's output); a view is build-time DDL (like a migration), not a scheduled job. open q: adopt dbt now vs alembic-view shortcut — leaning dbt because the NL→SQL AI use case needs documented marts as LLM context.
- 2026-08-28 — Production ingestion pattern — learned: OAuth consent is captured once and persisted, so a scheduler CAN poll each active token on the user's behalf (consent ≠ execution); pull belongs on a task queue + worker (arq/Celery = Sidekiq equivalent), not in the request handler; endpoint enqueues → 202; snapshots land append-only in CH, mutable orders go Postgres+CDC; reads hit the mart, decoupled from writes. open q/gap: callback stores no refresh token → scheduled pulls die when access token expires (real bug for production).
- 2026-08-28 — Don't couple EL to T — learned: ingestion job must NOT trigger dbt build; for a view there's nothing to refresh (live on read), for a materialized mart the scheduler runs a targeted `dbt run` batched — never per-sync. Reasons: single responsibility (dbt failure shouldn't lose data) + thundering herd (N syncs ≠ N dbt processes).
- 2026-08-28 — Scaling the dedup mart — learned: mart output is bounded (1 row/user); the ever-growing LANDING table is what makes a view slow (re-scans history per read) → materialize incrementally into ReplacingMergeTree keyed by user_id; partition landing on low-cardinality time (toYYYYMM(batched_at)), NOT user_id (high-cardinality partition key = CH footgun); order by user_id for selectivity. Concurrency: only the scheduler writes the mart (single locked run), so user-request concurrency is a non-issue; concurrent landing inserts are fine (CH is append-optimized). open q: view now vs incremental later — start with view, materialize when landing history makes reads slow.

- 2026-10-04 — First real end-to-end run of the dashboard sync + the "one-size-fits-all reader" question — learned: (1) **Testing auth without a frontend.** Cookie-only login (no bearer in the response body) is the *more* prod-grade choice — a token returned to JS must live in localStorage/memory and any XSS steals it; an `httponly` cookie can't be read by JS. The Swagger "Authorize" button is a red herring: `get_current_user` only offers HTTPBearer as a fallback, so calling `/auth/login` from `/docs` sets the cookie in the browser and every later `/docs` call carries it. For curl, a cookie jar (`-c` to save, `-b` to send) tests the *same* path the browser takes. Remaining prod gaps on the cookie: `secure=False`, no `max_age`, no `/auth/logout`. (2) **Vite proxy = same-origin.** `vite.config.js` maps `/api/*` → `:8000/*` (strips `/api`) and `/auth/*` → `:8000/auth/*` (no strip). The browser only ever talks to `:5173`, so there is no CORS preflight and the cookie rides along by default — that's why `fetchOrders()` works without `credentials: 'include'`. Pointing the frontend straight at `:8000` breaks both at once. (3) **pyarrow `decimal128()` needs args.** `pa.string()`/`pa.int32()` are fixed types; a decimal is *parameterized* — `Decimal(10,2)` and `Decimal(38,9)` are different types, so pyarrow demands `pa.decimal128(precision, scale)`. The values are NOT on `type_.precision` (empty) — they live at `type_.ch_type.prec` / `type_.ch_type.scale`, set in the child class `BigDecimal.__init__`, not on the `ClickHouseType` parent. Lesson: `dir(SomeClass)` lies about instance attributes; instantiate and inspect the object. Works for `Nullable(Decimal(...))` too — the wrapper still passes `isinstance(..., ChDecimal)`. (4) **Root cause of the reader bug, not the symptom.** `aiter_lines()` splits on `\n` and knows nothing about JSON — line breaks == record breaks ONLY in JSONL. `/v2/positions` returns one JSON *array*, so `json.loads(line)` yields a `list` and `json_data["user_id"] = ...` dies with "list indices must be integers"; `/v2/account` returns one object that works *by luck* on one line and breaks the day Alpaca pretty-prints. Deeper cause: `stream_records` fused two concerns — "how does this API deliver bytes" (different per endpoint) and "how do I make rows" (same for all) — and the model↔URL↔parse triple was split across router and worker so nothing owned it. Fix shape = a per-source adapter (the Singer/Airbyte connector pattern: generic loader + one small adapter per source); I'd built the loader and skipped the adapter. (5) **Streaming bytes ≠ streaming records.** I wanted one generic path and reached for `aiter_lines`; the actual generic contract is the **async generator** (`async def ... yield record`). Outside stays `async for record in ...` forever; inside, account does 1 GET and yields once, positions does 1 GET and yields N, orders later loops `page_token`, a genuinely-JSONL API uses `aiter_lines`. Keep the generator, change only its insides — `payload = response.json()`, then `records = payload if isinstance(payload, list) else [payload]`. (6) **Alpaca pagination facts:** `/v2/account` and `/v2/positions` do NOT paginate (positions is bounded by portfolio size, a few hundred rows); `/v2/orders` has `limit` (default 50, max 500) + `page_token`, `/v2/account/activities` and `/v2/options/contracts` have `page_token`. So don't build paging today — just don't hard-code "one GET" into the worker. (7) **If a response really is too big, before scaling infra:** ask the API for less (pagination/filters — push work to the server), else swap in a streaming JSON parser (`ijson`), else spill to disk. **ijson = SAX vs DOM**, i.e. a DB cursor vs `fetchall()`: it emits `start_array / start_map / key / string / end_map` events as bytes arrive, and `ijson.items(f, "item")` rebuilds just the small object between `start_map`/`end_map`, yields it, throws it away — memory holds 1 record, not 1M. Path language: `"item"` = element of the top-level array, `"results.item"`, `"data.rows.item"`. Not installed in the venv; not needed yet. Interview line: "`.json()` because positions is bounded by portfolio size; unbounded → `page_token`; one giant array with no paging → `ijson` for flat memory — and the generator interface means none of those touch the worker." Still open/unfixed: `ingest_data_to_CH(...)` and `client.insert(...)` both unawaited (job logs SUCCESS, ClickHouse stays EMPTY — the worst failure mode), `user_id` passed as a `UUID` object where pyarrow wants a string, and the worker still receives a live SQLAlchemy class + a decrypted bearer token through the Redis queue.
- 2026-10-04 — `uv add` hung forever; root cause was MTU, not uv — learned: WSL2 `eth0` was at MTU 1500 while something on the Windows side (VPN) added encapsulation, so oversized packets were silently dropped. The symptom set is the lesson: DNS resolved, `ping 1.1.1.1` was 0% loss, raw TCP connect to :443 succeeded — but every HTTPS request hung until timeout, because only the TLS handshake sends full-size packets. Everything *looked* connected. One-command test: `ping -M do -s 1472 <ip>` (payload + 28 = MTU); it failed 100% at 1472 and passed at 1272, so `sudo ip link set dev eth0 mtu 1280` fixed it (persist via `[boot] command = ...` in /etc/wsl.conf, since it resets on `wsl --shutdown`). Rule to keep: **ping works but HTTPS hangs → suspect MTU.** Also a method note — my own diagnostic shell is network-sandboxed, so my first curl timings were my sandbox, not his machine; I nearly diagnosed IPv6 off that. Verify *whose* network you're testing before you name a cause.

- 2026-11-01 — sync vs async in FastAPI (learned with a demo: 3 requests × 1s blocking call) — learned: `async def` routes all share ONE event-loop thread and only switch at an `await`; a sync call inside (psycopg2, sync SQLAlchemy, CH SQLAlchemy) blocks EVERY request on the API, so 3 requests take 3s instead of 1s. `def` routes run in FastAPI's threadpool (40 threads by default), which effectively adds the `await` for you (`asyncio.to_thread`). `await` on a sync function doesn't help: the call runs and blocks first, then fails with `TypeError: 'int' object can't be awaited`. Rule: async library inside → `async def`; sync library → `def`; never sync inside `async def` ("worst of both"). Applied (Claude did the edit at his request): `register`, `login`, `alpaca_callback` (sync `httpx.Client` now), `account_overview` → `def`; `alpaca_connect` and `/dashboard/sync` stay async.
- 2026-11-01 — Scaling login (notes for later, not built) — learned: login is CPU-bound on purpose (PBKDF2 100k iterations), so the GIL makes more threads not help much: the real limit is cores. Scale in layers: (1) threads (`def` → pool of 40), (2) processes (`uvicorn --workers N`, about 1 per core; Dockerfile has 1 today), (3) machines (replicas behind a load balancer; works with no code change because auth is a stateless JWT cookie), (4) rate limiting per IP/account. Hidden bottleneck = DB connections: SQLAlchemy pool 5+10 per process × workers × replicas quickly passes Postgres max_connections (~100) → PgBouncer (same problem as Spark executors flooding a JDBC source). Login happens once; later requests only verify the JWT (cheap), and at huge scale auth moves to a dedicated service (Auth0/Cognito/Keycloak). Security issues found in crypto.py (open, not fixed): `==` hash comparison is not constant-time → use `hmac.compare_digest`; 100k PBKDF2 iterations is below OWASP's 600k (or switch to argon2/bcrypt), with more iterations meaning more CPU per login.
